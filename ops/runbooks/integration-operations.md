# Integration operations

Running partner integrations: partner setup, request signing, the inbound endpoint and file drop, message statuses, automatic retries, operator replay and retry, and reconciliation. Integrations give an exactly-once business effect over at-least-once delivery (journey J-10).

Sources (under `apps/automotive_core/automotive_core/integration_hub/`):

- `partners.py`, `signing.py`, `inbound.py`, `outbox.py`, `idempotency.py`, `maintenance.py`, `contracts.py`
- `adapters/https.py`, `adapters/file_drop.py`, `adapters/edi.py`
- message handlers: `apps/automotive_supply_chain/automotive_supply_chain/integrations/handlers.py` and `apps/automotive_manufacturing/automotive_manufacturing/mes/handlers.py`
- API contract: `integration_hub/openapi.json` (generated by `scripts/dev/openapi.py`)

**Who:** IT Operator or System Manager. Auditors can read messages and run the reconciliation. Desk entry points:

- `/desk/integration-partner`
- `/desk/integration-inbound-message`
- `/desk/integration-outbound-message`
- `/desk/automotive-settings`

## Settings (Automotive Settings, integration section)

| Field | Default | Effect |
|---|---|---|
| Outbound Host Allowlist | empty | One hostname per line. Webhooks go only to `https://` URLs whose host is listed (no redirects, 10 s timeout). Empty means no HTTPS delivery at all. |
| Webhook Tolerance Seconds | 300 | Allowed clock skew of inbound signatures; nonces are kept for twice this time |
| Outbox Max Attempts | 8 | Outbound delivery attempts before Dead Letter |
| Outbox Base Backoff Seconds | 30 | Base of the exponential backoff (inbound and outbound): `min(base × 2^(attempt−1), 3600)` seconds |
| Inbound Max Attempts | 6 | Processing attempts before an inbound message is dead-lettered |
| Inbound Rate Limit Per Minute | 120 | Requests per partner per minute on the HTTPS endpoint (HTTP 429 above) |

## Partners

Create one **Integration Partner** per counterpart:

| Field | Notes |
|---|---|
| Partner Code | Upper-cased; it is the record name and the value of the `X-Hinode-Partner` header |
| Partner Type, Party Type / Party | Party links the partner to its Supplier or Customer. Events published for a party go only to partners of that party. |
| Adapter | **Local File Drop** (default) or **HTTPS Webhook** |
| Message Format | **JSON** (default) or **Hinode EDI** |
| Service User | Required when *Allowed Message Types* is set, and must be enabled. Inbound messages are processed **as this user**, so its normal permissions apply. |
| Endpoint URL, Key ID, Outbound Secret | HTTPS delivery: the URL must be `https://` and allow-listed. Key ID is sent as `kid=`. |
| Inbound Secret | Shared secret the partner signs requests with |
| Previous Inbound Secret, Previous Secret Accepted Until | Set by *Rotate Inbound Secret*: the replaced secret, still accepted until that time (see [Rotating partner secrets](#rotating-partner-secrets)) |
| Allowed Message Types | One per line; empty means nothing is accepted |
| Subscribed Events | Outbound event types, one per line |

Service User requirements of the message handlers:

- `asn`, `po_acknowledgement` and `inventory_adjustment`: a **supplier portal user**, that is a Website User with active Partner User Access to the partner's Supplier. Otherwise the message is Rejected with "service user is not a Supplier portal user".
- `dealer_order` and `dealer_order_change`: a **dealer portal user** (Customer).
- `production_event`: a user with read access to the reported Work Order. Its plant User Permissions limit which orders it may report.

Inbound message types:

- Accepted by the envelope: `dealer_order`, `dealer_order_change`, `asn`, `po_acknowledgement`, `production_event`, `inventory_adjustment`, `supplier_invoice`, `shipment_status`, `bank_statement`.
- With a registered handler: `asn`, `po_acknowledgement`, `dealer_order`, `dealer_order_change`, `production_event` and `inventory_adjustment`.
- `supplier_invoice`, `shipment_status` and `bank_statement` have **no handler yet**. Messages of those types are Rejected ("no handler registered for …"), so do not allow them for a partner.

What the `inventory_adjustment` handler does:

- It handles a supplier's count of the consignment (VMI) stock it owns at our plant.
- It creates a **draft Cycle Count** with expected and counted quantities per item and batch; it never changes stock directly.
- A warehouse clerk reviews and posts the count; consignment counts post at zero value.
- It requires an active Consignment Agreement for the warehouse, and only consigned items.
- Resends with the same count reference return the same Cycle Count.

Outbound events published by the applications: `purchase_order.submitted`, `supplier_schedule.published`, `shipment.dispatched`, `dealer_order.received`, `dealer_order.accepted`, `dealer_order.rejected`, `dealer_order.changed`.

**Connection Status** is computed on save and after each delivery. It never shows Live for an unconnected partner:

| Value | Meaning |
|---|---|
| Local Adapter Only | File-drop partner |
| Not Configured | HTTPS partner without an allow-listed `https://` endpoint or without an outbound secret |
| Configured (Unverified) | Configured, but no successful delivery yet, or the last attempt failed |
| Live | The last delivery succeeded |

*Last Success At*, *Last Failure At* and *Last Error* show delivery health.

## Signing (both directions)

```text
X-Hinode-Signature: t=<unix seconds>,kid=<key id>,n=<nonce>,v1=<hex hmac>
v1 = HMAC_SHA256(secret, "<t>.<n>." + raw request body)
```

- **Inbound** (`receive`): the server checks, in this order:
  1. the partner exists (`X-Hinode-Partner`);
  2. the rate limit;
  3. the partner has an inbound secret;
  4. `t` is within the tolerance;
  5. the nonce is 8–64 alphanumeric characters;
  6. the HMAC matches the inbound secret or, during a rotation's overlap, the previous one;
  7. the nonce was not used before. Nonces are stored in Integration Nonce; a replay gives "Replayed request (nonce already used).".

  `kid` is parsed but not used to select the secret: the current secret is tried first, then
  the previous one while its overlap lasts.
- **Outbound** (HTTPS Webhook): requests are signed with the partner's *Outbound Secret*. `kid` is the Key ID, or the partner code if Key ID is empty. Other headers sent:
  - `Content-Type`: `application/json`, or `application/edi-x12` for Hinode EDI;
  - `User-Agent: toyota-erp-clone-outbox/1`;
  - `X-Hinode-Event`;
  - `X-Hinode-Delivery`: the outbound message name;
  - `Idempotency-Key`;
  - `X-Correlation-ID`.

  Receivers should deduplicate on `Idempotency-Key` or the envelope's `event_id`.

Connectivity test with a test partner whose *Allowed Message Types* include `asn` (any shell with `openssl` and `curl`; the body must be byte-identical to what is signed):

```bash
SECRET='<inbound secret of the partner>'
body='{"message_id":"TEST-0001","message_type":"asn","schema_version":"v1","data":{}}'
t=$(date +%s); n=$(openssl rand -hex 16)
sig=$(printf '%s.%s.%s' "$t" "$n" "$body" | openssl dgst -sha256 -hmac "$SECRET" | sed 's/^.* //')
curl -sS -X POST "https://$SITE/api/method/automotive_core.integration_hub.inbound.receive" \
  -H "X-Hinode-Partner: <PARTNER_CODE>" -H "X-Hinode-Signature: t=$t,kid=test,n=$n,v1=$sig" \
  -H 'Content-Type: application/json' --data-binary "$body"
```

Expected response:

- **202** with `"status": "accepted"` and an `inbound_id`.
- The empty `data` above passes the envelope but is then **Rejected** by the `asn` handler (invalid AsnMessage), which is visible in the desk. This proves the signing path without creating business documents.
- Sending the same request again gives 401 (nonce replay).
- Re-signing the same body with a new nonce gives **200** with `"status": "duplicate"`.

## Inbound endpoint and responses

`POST /api/method/automotive_core.integration_hub.inbound.receive` (guest endpoint, authenticated by the signature).

The envelope is validated strictly (`contracts.InboundEnvelope`, extra fields refused):

- `message_id`: 1–100 characters of `A-Za-z0-9._:-`;
- `message_type`;
- `schema_version`: `v1`;
- optional `sent_at`;
- `data`: an object.

The payload of `data` is validated by the handler's model (`AsnMessage`, `AckMessage`, `DealerOrderMessage`, `DealerOrderChangeMessage`, `InventoryAdjustmentMessage`, `ProductionEvent`).

| HTTP | Meaning |
|---|---|
| 202 | Stored and queued (`status: accepted`) |
| 200 | Same partner + `message_id` + identical payload already received (`status: duplicate`, with the original processing status and result document) |
| 401 | Unknown partner, no inbound secret, bad or expired signature, or nonce replay |
| 403 | Partner inactive, or message type not allowed for the partner |
| 409 | `message_id` already used with a different payload |
| 417 | Invalid envelope or EDI ("Invalid message: …") |
| 429 | Rate limit exceeded |

A database unique key on (partner, message_id) backs the duplicate check ([database.md](database.md#unique-keys)).

## Inbound statuses and automatic retries

| Status | Meaning | Next step |
|---|---|---|
| Received | Stored; a job on the `short` queue processes it | automatic |
| Processing | (status value; Received/Processing older than 5 minutes are re-queued) | automatic |
| Processed | The handler created or found the business document (*Result DocType / Name*). The status is written in the same transaction as the documents. | none |
| Failed | The handler raised an error; *Last Error* holds it; *Next Attempt At* = now + backoff | automatic retry |
| Dead Letter | Failed *Inbound Max Attempts* times | operator: fix cause, **Replay** |
| Rejected | Can never succeed as sent: no handler, invalid payload, wrong partner or reference | operator: fix data or partner config, Replay or ask partner to resend |

- **Scheduler, every minute:** `automotive_core.integration_hub.inbound.retry_due` re-queues up to 200 due Failed messages and up to 200 stale Received/Processing messages.
- **Audit:** Dead Letter and Rejected outcomes are written to the audit chain (`integration.inbound.dead_letter`, `integration.inbound.rejected`).

## Outbound statuses and automatic retries

Events are written to **Integration Outbound Message** in the same transaction as the business change (transactional outbox). There is one message per partner, with a unique idempotency key.

| Status | Meaning |
|---|---|
| Pending | Waiting for dispatch (due at *Next Attempt At*) |
| Sending | Claimed by a dispatcher. If still Sending after 10 minutes (dead worker), it is set back to Failed and due again. |
| Delivered | 2xx from the endpoint, or file written for file drop |
| Failed | Retryable failure: network error (code 0), 408, 409, 425, 429 or 5xx. Retried after the backoff. |
| Dead Letter | Permanent failure (any other non-2xx, or an allowlist/secret problem) or *Outbox Max Attempts* reached |

- **Dispatch:** `automotive_core.integration_hub.outbox.dispatch_due` runs every minute and right after an event is published. It claims due messages with `FOR UPDATE SKIP LOCKED`, so several workers are safe.
- **Delivery history:** every attempt is recorded in the message's *Delivery Attempts* table (attempt no, time, duration, response code, outcome, error).
- **Audit:** Dead letters are audited (`integration.outbound.dead_letter`).

## Operator actions: Replay and Retry Delivery

Shown on the form only to IT Operator and System Manager.

- **Integration Inbound Message → Replay** (status Failed, Dead Letter or Rejected).
  - Sets the message back to Received and queues it again. Audit: `integration.inbound.replayed`.
  - API: `POST /api/method/automotive_core.integration_hub.inbound.replay` with `name`.
- **Integration Outbound Message → Retry Delivery** (status Failed or Dead Letter).
  - Sets it to Pending, due now. Audit: `integration.outbound.retried`.
  - API: `POST /api/method/automotive_core.integration_hub.outbox.retry` with `name`.

Neither action resets the *Attempts* counter. A dead-lettered message that fails again after a replay or retry goes straight back to Dead Letter: each operator action buys one attempt. Fix the cause first, for example:

- add the host to the allowlist;
- correct the endpoint or secret;
- fix the referenced master data;
- give the service user the missing permission.

There is no bulk replay or retry action (not implemented yet); act per message.

Procedure for a dead-letter alert (`ErpOutboxDeadLetters` / `ErpInboxFailures`, see [monitoring.md](monitoring.md)):

1. List the messages: filter Status = Dead Letter, Failed or Rejected; group by partner.
2. Open one and read *Last Error*. For outbound messages, also read the *Delivery Attempts* rows and the partner's *Last Error*.
3. Fix the cause.
4. Replay or Retry Delivery each affected message.
5. Watch the message reach Processed or Delivered.
6. Run the reconciliation (next section).

## Reconciliation

`GET /api/method/automotive_core.integration_hub.inbound.reconciliation` (IT Operator, System Manager, Auditor), or from the host:

```bash
./scripts/deploy/compose.sh "$ENV" exec -T backend bench --site "$SITE" execute \
  automotive_core.integration_hub.inbound.reconciliation
```

It returns:

- `by_status`: message counts per status;
- `processed_without_result_document`: Processed messages whose result document no longer exists;
- `deduplicated_by_business_reference`: several messages answered with the same document. This is information only: handlers deduplicate on the partner's own reference, for example the supplier's ASN number.
- `ok`: false if any Processed message points to a missing document.

Run it after every incident and replay. The seed validation's "inbound messages exactly once" check relies on the same function.

## File-drop adapter (local exchange)

For partners without a live connection. Each partner directory is `sites/<site>/private/integration/<PARTNER_CODE>/` in the sites volume.

These directories are **not in the backups**: `bench backup --with-files` archives only `public/files` and `private/files`. Accepted messages are kept in the database (Integration Inbound Message), but unprocessed inbox files and outbox files exist only on the host.

Subdirectories:

| Directory | Content |
|---|---|
| `outbox/` | Outbound messages, written atomically as `<OUT-…>.json` or `.edi` |
| `inbox/` | Files the partner drops for us (`.json` or `.edi` only) |
| `processed/` | Accepted inbox files |
| `rejected/` | Inbox files that failed validation, each with `<name>.error.txt` |

- **Polling:** every minute for each active Local File Drop partner (`automotive_core.integration_hub.partners.poll_file_drops`). Each file goes through the same accept path as HTTPS, without the signature: storage once per message id, then queued processing.
- **Transfer:** moving files between these directories and the partner (SFTP or similar) is **not implemented**. Use your own transfer agent.
- **Manual drop for a test.** Stream the file in through `exec` so it is created by the `frappe` user, under a temporary name first; only `.json` and `.edi` files are picked up:

  ```bash
  ./scripts/deploy/compose.sh "$ENV" exec -T backend bash -c \
    "cat > sites/$SITE/private/integration/<PARTNER_CODE>/inbox/asn-0001.json.part" < ./asn-0001.json
  ./scripts/deploy/compose.sh "$ENV" exec -T backend mv \
    "sites/$SITE/private/integration/<PARTNER_CODE>/inbox/asn-0001.json.part" \
    "sites/$SITE/private/integration/<PARTNER_CODE>/inbox/asn-0001.json"
  ```

## Hinode EDI format

A project-defined, X12-inspired flat format (`adapters/edi.py`). It is **not** ANSI X12 or EDIFACT; a real standard needs a partner-specific adapter.

- Segments end with `~`; elements are separated by `*`.
- `?` escapes `*`, `~` and `?`.

```text
ISA*HINODE*1*<interchange control>~
ST*<message or event type>*<message id>~
BGN*<schema version>*<sent / occurred at, ISO-8601>~
DTA*<json path>*<type S|N|B|Z|O|L>*<value>~     one per leaf of "data"; lists become index paths (lines.0.qty)
SE*<segment count including ST and SE>*<message id>~
IEA*1*<interchange control>~
```

Decoding fails with a clear reason in each of these cases:

- missing ISA/IEA or ST/SE;
- a segment-count mismatch;
- the SE id differs from ST;
- the ISA and IEA control numbers differ;
- a bad DTA segment;
- an unknown value type;
- an unexpected segment.

Inbound EDI failures answer 417. In file drop they go to `rejected/` with the reason.

## Housekeeping and monitoring

- Daily `automotive_core.integration_hub.maintenance.prune` deletes Integration Nonces older than twice the tolerance, and expired Idempotency Records (kept 7 days).
- Metrics: `erp_outbox_messages{status=Pending|Failed|Dead Letter}` and `erp_inbox_messages{status=Failed|Dead Letter|Rejected}`. Alerts: `ErpOutboxDeadLetters`, `ErpInboxFailures`. Grafana panels: *Outbox*, *Inbox problems*. See [monitoring.md](monitoring.md).
- Correlation: every message stores the correlation id of the request or job that created it. Outbound webhooks send it as `X-Correlation-ID`. See [monitoring.md](monitoring.md#logs-and-correlation-ids).

## Rotating partner secrets

**Inbound**, with an overlap so the partner switches without refused requests:

1. On the partner, an IT Operator or System Manager chooses **Rotate Inbound Secret** and
   the overlap in hours (default 24, at most 168). The same call over the API:
   `POST /api/method/automotive_core.integration_hub.partners.rotate_inbound_secret` with
   `partner` and `overlap_hours`.
2. The new secret is generated on the server (32 random bytes, URL-safe) and shown **once**.
   Give it to the partner over a secure channel; it cannot be displayed again (rotate again
   if it is lost).
3. Until *Previous Secret Accepted Until*, requests signed with either secret are accepted.
   Each one still signed with the old secret writes
   `integration.inbound.previous_secret_used` (with the partner) to the structured log, so
   you can see whether the partner has switched before the overlap ends.
4. After that time the old secret gets 401; partners resend (at-least-once), and a duplicate
   resend is harmless.

An overlap of 0 replaces the secret at once (for a leaked secret). A second rotation during
an overlap ends the first overlap: only the secret being replaced stays valid. Each rotation
is recorded as the audit event `integration.inbound_secret_rotated` (the overlap, never the
secret). Pasting a new value into *Inbound Secret* by hand still works, with no overlap of its own.

**Outbound:** update *Outbound Secret* (and *Key ID* if the partner selects keys by `kid`),
at the time agreed with the partner: the partner checks one secret, so the two sides switch
together. Deliveries refused meanwhile are retried automatically.

Secrets are Password fields, encrypted with the site's `encryption_key` (`site_config.json`). See [security-operations.md](security-operations.md#secrets).
