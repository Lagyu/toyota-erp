# Requirements Traceability Matrix

Toyota ERP Clone (Hinode Automotive Group ERP) · requirement → implementation → evidence · 2026-10-24

## 0. About this matrix

**Purpose.** This matrix maps every requirement in *Toyota ERP Clone: High-Level Product & Engineering
Requirements* v1.0 (2026-10-24) to the code that implements it, the automated tests and recorded runs that
back it up, its status and its known limits. It is acceptance gate 10 of §8.2 and the
`REQUIREMENTS_TRACEABILITY.md` deliverable of §10. Nothing is shown as passing unless §0.3 records a run.

**Baseline.** The baseline is the commit [`563edb2`](https://github.com/Lagyu/toyota-erp/commit/563edb2ea83085ccd2c9b89fd14b528c374b54a0), the HEAD of `main` on 2026-10-24 (UTC); this document, the
scan in findings.md and licences.md were committed after it, changing no code. Statuses come from
reading the code at that commit. No tests were run while writing this matrix: test results are the GitHub
Actions runs listed in §0.3. Decision IDs (D-0xx) refer to [DECISIONS.md](DECISIONS.md), finding IDs (V-xx,
C-xx) to [ops/security/findings.md](ops/security/findings.md).

**Status legend.**

| Status | Meaning |
|---|---|
| **Done** | Implemented in the code at the baseline, and covered by automated tests (the server, unit, API and browser suites that CI runs) or by a recorded workflow run (§0.3). A part that is exercised but not asserted, or a branch the requirement does not name (an error path, a second threshold, an alternative endpoint) that nothing exercises, is named in Notes and listed in §10.3. |
| **Partial** | Partly implemented; or a capability the requirement names is exercised by no automated test or run; or the requirement asks for a measured result that the repository does not record. The gap is stated in Notes and listed in §10. |
| **Pending** | Not implemented, or nothing recorded yet. Listed in §10. |

A status says what the code and its tests cover, not whether the tests passed: that is recorded in §0.3. A row
whose cited tests fail, are skipped or have not run in those runs falls back to Partial.

**Evidence column.** The test classes and files named there run in every CI run: the server suites, unit
tests and API tests in the CI run (§0.3), the browser specs in the e2e run (§0.3). Evidence from other runs is named by its
placeholder (the smoke test (§0.3), the rehearsal (§0.3), the standard dataset run (§0.3), the load test (§0.3)). A number in brackets after a class is
its number of tests.

### 10.4 Limits stated in the runbooks and findings
- **Findings awaiting the owner** ([findings.md](ops/security/findings.md)): V-02 (Debian packages without a fix), V-03c (Pillow, critical), V-03d (pypdf), V-03g (pdfkit), V-05 (realtime server Node packages), C-03 (no network-level egress filtering: the application allowlist is the only outbound control). Accepted without an owner flag: V-03e, V-03f, C-05 (secrets on `bench` command lines during site creation and restore). Mitigated: V-04, C-01 (CSP without `script-src`), C-06 (no outgoing mail account set up by the deploy scripts), C-08 (recovery point measured on test sites only).
- **Availability:** one host is the delivered topology; the HA option is not packaged and not rehearsed, and 99.9 % is not claimed ([high-availability.md](ops/runbooks/high-availability.md)).
- **Recovery:** RPO about 5 minutes by design, measured on test sites only; RTO not validated on real data. Only whole-site restores exist: single-document or single-file restore is not implemented. Only the last three nightly sets can be brought forward from the newest binary-log snapshot, and a replay cannot leave out one bad transaction. The integration file-drop directories and `private/ops` (drill evidence) are not backed up. Missed scheduled runs are not caught up. Off-host copy protection (versioning, object lock) is not configured by the repository ([backup-restore.md](ops/runbooks/backup-restore.md)).
- **Not scripted:** rotation of the database root password (manual procedure), of a site's own database password, and of the restic and Grafana passwords (manual); creation of the MariaDB monitoring account; outgoing e-mail setup ([security-operations.md](ops/runbooks/security-operations.md)).
- **Manual after install:** the Alertmanager receiver.
- **Not implemented:** bulk replay or retry of integration messages; central log shipping; network-level egress filtering; transfer of file-drop files to partners (SFTP); audit purging and retention (audit events are kept indefinitely); health reporting of missing database triggers; an access-review record in the application; restic backends other than S3 ([integration-operations.md](ops/runbooks/integration-operations.md), [database.md](ops/runbooks/database.md), [access-review.md](ops/runbooks/access-review.md), [monitoring.md](ops/runbooks/monitoring.md), [install-fresh-host.md](ops/runbooks/install-fresh-host.md)).
- **Integration format:** Hinode EDI is a project format (X12-inspired), not ANSI X12 or EDIFACT (D-010).
- **Identity providers:** Frappe does not ask its OTP for social logins, so the provider must enforce MFA; LDAP group mappings must stay empty; SAML is not supported by Frappe.
- **Finance:** group consolidation is a management view without elimination entries (D-021); tax rates are ERPNext's country defaults and jurisdiction-specific compliance is not validated.
- **Proxy:** nginx trusts `X-Forwarded-For` from any address, safe only behind Traefik (`TLS_MODE=none` lets clients spoof their address). IT Operator includes System Manager.
- **Performance environment:** results come from a hosted runner (4 vCPU, 16 GB) shared with the load generator ([ops/performance/README.md](ops/performance/README.md)).
